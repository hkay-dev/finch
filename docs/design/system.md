# Design system

Every size, alpha and motion length the views use is a named `pub const` in `src/tokens.rs`, grouped by section (type, spacing and sizes, fills and color, dark and light themes, motion). Each has a `///` line saying where its value came from. Views take their values from there; a value that is settings-driven (panel widths, the editor font size) or computed at paint time keeps its `px(` in the view with a trailing `// design: <why>` comment. Text and wash colors come from the theme at the token alphas. The code palettes are the one place a color is written out: `PALETTE_<SCHEME>_<DARK|LIGHT>` tables (25 schemes, listed in the Code colors guide page; each scheme's published hex values with the source file on its `///` line, one table per appearance, picked by `[code_colors] scheme`) that `theme::set` lays over the kit's highlight theme, so the vendored `default-theme.json` decides no code color (its `syntax` block is empty). Xcode's are the default; the vivid lift (`tokens::vivid`) and the `[code_colors.dark|light]` role overrides are applied on top (see the Code colors guide page). With the colored roles off, plain code, fields, variables and operators are the app's text ink at `ALPHA_PRIMARY` (which is also `theme.foreground`, the editor's text color), punctuation is the secondary ink, and no code role sets a weight, so nothing is bolder than the code font. The editor's own copies of the ink curve and selection alphas (`vendor/gpui-base/.../system_look.rs`) carry `// mirrors tokens::<NAME>` comments, and a unit test fails if one drifts.

Rules for a token: one `pub const` with the `///` source line directly above and the value on the same line; a light-theme value sits beside its dark twin as `<NAME>_LIGHT`; a new surface adds a section.

The table is generated: run `scripts/tokens.sh` after editing `src/tokens.rs`. It rewrites everything between the markers below.
